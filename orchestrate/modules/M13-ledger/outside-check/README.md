# The outside check (template)

An hourly check that runs on GitHub, not on the Mini, so it still works if the Mini is off or has gone wrong
(R-0b-72; design v4 §8 E6). The Mini watches that this keeps running (`M12-sensors/outside-watch.mjs`), and this
watches the Mini. Copy this folder into its own **public** repo. Public means Actions minutes are free; the logs are
public too, so the check prints only "product N / <check>: ok|FAIL <reason code>".

| File | What it does |
|---|---|
| `.github/workflows/outside-check.yml` | The schedule. Generated by `node workflow.mjs`; never edit it by hand. |
| `outside-check.mjs` | The six checks for one product: heartbeat, audit files, audit runs, live deploy, Actions permission, robot merges. Plus one `product 1 / repo-guard` step that checks this repo itself (lead call L24): only the owner can write, deploy keys are read-only, an active rule on the default branch blocks every other push (only the admin role may get past it), and the check's own token can't write. Anything it can't read is a FAIL. |
| `pinned-docs-lane.json` | Per product slot: the paths the robot may merge alone (its first-cutover docs lane). Empty in the template. |
| `acknowledged-merges.json` | Per product slot: SHA-256 of each robot merge the owner has looked at and accepted. Empty in the template. |
| `robot-merges-owner.json` | `tags`: a short public tag per slot (8–32 lowercase letters or digits) that the PRODUCTS entry and the Mini's config must repeat; `cleared`: per slot, the time the owner last cleared a latched robot-merges red. Empty in the template. |
| `collect.mjs`, `notify.mjs` | One updated issue in this repo per failing check, closed when it passes. |
| `keep-alive.mjs` | A small commit to the `keep-alive` branch (never the default branch) after 50 quiet days, so GitHub doesn't switch the schedule off. |
| `supported.mjs` | A copy of Bob's M12 rule for "a supported main commit"; a Bob test keeps the two identical. |
| `pinned-audit-files.json` | Per product slot: each audit file's path and SHA-256, as approved. Empty in the template. |

The product list is the `PRODUCTS` Actions secret, never a file:
`[{ "repo": "owner/name", "stage": "first", "post_merge_audit": false, "audit_workflow": "audit.yml", "robot": "robot-login", "tag": "slot tag" }]`.
Slot 1 is the first entry. Each slot's only public name is "product N". At most 3 entries (more fails every slot). A product with no production site
adds `"no_production": true`; otherwise "no live production deploy found" is a FAIL.

## Owner steps (Joe)

These are the real halves of R-0b-72's "done when"; Claude has tested the code only against fakes. Bob's plain-language
step format applies; the Front Door or the Lead turns each into paste-ready steps with the real names.

1. **Make the repo.** On github.com, a new public repo under the owner account; copy this folder's files in, except `outside-check.test.mjs` (it is Bob's test).
2. **Make the read-only key** (run `/apikeys` first). A fine-grained token for the product repos only, read-only:
   Contents, Metadata, Actions, Deployments, Issues, Administration. Add **this** repo too, with Metadata and
   Administration read-only (the repo guard reads its collaborators and rules), and nothing that writes: the
   keep-alive branch and the alert issues use the run's own built-in token. Save it as the `CHECK_TOKEN` Actions secret.
3. **Save the product list** as the `PRODUCTS` Actions secret (the shape above).
4. **Pin the audit files.** For each product, ask Claude for the `pinned-audit-files.json` entry (paths and SHA-256 of
   the approved audit files on main) and commit it.
5. **Pin the docs lane.** For each product, ask Claude for the `pinned-docs-lane.json` entry (a copy of the docs-lane
   paths in that product's first-cutover rules entry) and commit it. With no entry, robot-merges FAILs and the Merge Gate stays shut.
   If robot-merges FAILs on a merge you have looked at and accept, ask Claude for its `acknowledged-merges.json` line and commit it.
   **Tag the slot:** ask Claude for a new tag for each product; put it in `robot-merges-owner.json` under `tags`, in
   that product's `PRODUCTS` entry as `"tag"`, and in the Mini's config (step 6). The tag is not secret; it only makes
   sure slot 1 is the product the Mini thinks it is.
6. **Set the Mini's watch.** In the Mini's private config: this repo's name, the home repo for "stopped" alerts, and
   each slot's product name and tag (`product 1` → the first product, its tag) so the Mini records robot-merges' last
   green time. **Clear the first latch:** the Mini starts with the gate shut. After the first green run, put the
   current time in `robot-merges-owner.json` under `cleared` for that slot (Claude gives you the line) and commit it.
   Do the same after a robot-merges red you have dealt with, or after the Mini was off for more than 5 days.
7. **Lock this repo** (lead call L24). Settings → Rules → Rulesets → New branch ruleset: target the default branch,
   enforcement Active, turn on "Restrict updates", "Restrict deletions" and "Block force pushes", and in the bypass
   list add only the Repository admin role (not "all branches", so the keep-alive branch still works). Settings →
   Collaborators: nobody but you. Deploy keys: none, or read-only. The Mini's tokens and the robot accounts get no
   write access here. If any of this slips, the next run shows `product 1 / repo-guard: FAIL <reason>` and the Merge
   Gate shuts.
   **Prove the write test once:** the guard tells "this token can write" apart from "can't" by GitHub's answer to a
   ref it will never create (403 or 404 = can't, 422 = can). That reading comes from GitHub's docs, not yet from a
   real run (checked October 2026). So once, swap `CHECK_TOKEN` for a token that can write here and run the workflow
   by hand: it must show `FAIL check-token-can-write`. Then put the read-only token back.
8. **Check it.** After the first hourly run, the Actions tab shows a green run.
9. **Stop it on purpose** (Actions tab → the workflow → Disable workflow): within about 2 hours an issue
   "The hourly outside check has stopped running" appears in the home repo. Enable it again; the issue closes.
10. **After a week:** the account's Billing → Usage page shows 0 Actions minutes for this repo.
11. **From a second GitHub account:** open a PR and an issue on this repo; the Actions tab shows no new run.
12. **Day 61** (put it in your calendar on the day the repo is made): the Actions tab still shows hourly runs. If the
    schedule was switched off, a commit on the `keep-alive` branch doesn't count as activity (not yet tested; GitHub's
    docs, October 2026, don't say which branch counts): tell Claude, who will change the plan.
13. **Prove robot-merges on the test repo first** (before any real product; lead call L20). With the test repo as
    product 1: have the robot merge a PR that changes only a docs-lane file → the next hourly run shows
    `product 1 / robot-merges: ok`. Then have it merge one that changes a file outside the lane → `FAIL
    robot-change-outside-docs-lane 1`, and the Mini's Merge Gate fact turns red. After two hourly runs it stays red
    (latched). Acknowledge that merge → the check is ok again, but the gate stays shut until you add a `cleared` time.
    **When you move from the test repo to the real product, give the slot a new tag** in all three places; the old
    tag then no longer matches and the gate stays shut until all three agree.
