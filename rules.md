# Bob's rules

**The one home for Bob's numbered rules** (D-028, 2026-10-29). Before that, Rules 1–15 were written out in both `build-protocol.md` and `build-protocol-core.md` (in different words, and for a while numbered differently), Rules 16–33 lived only in the core, and `skill/SKILL.md` and `AGENTS.md` each carried their own "key rules" summary.

- **Numbers are permanent labels.** A rule keeps its number wherever it is filed; the groups below are ordered by *when you need the rule*, not by number.
- **`build-protocol-core.md` holds a one-line index** (number, title, how it is enforced, group). Read group 1 at the start of every session, and each later group in full at the stage it names.
- **The text of each rule is moved word for word** from where it was written. Rules 1–13 and 15 use the fuller wording that was in `build-protocol.md`; the core's shorter versions of 1–13 became the index.

> **Enforceability tags (Rule 33).** `HOOK` = a hook blocks it · `SCRIPT` = a runnable checker exists · `GATE` = a named gate stops on it · `PROSE` = nothing enforces it; it depends on the reader remembering. **Tagging is not decoration — a `PROSE` rule is a wish, and Rule 31 forbids closing a *recurring* class with one.** Honest current state: Rules 1–30 are `PROSE` except Rule 23 (`SCRIPT`: `coherence-check.sh`, whose class [8] checks the root file since D-018), Rule 28 (`SCRIPT`: `spec-audit.py`), and Rule 30's ledger clause (d) (`SCRIPT`: `audit-ledger-check.mjs`, D-018). "Merge only on green" is `HOOK` since D-018 (the merge guard, Step 6b item 6). Rules 31–33 carry their tags inline, as they actually stand today, not as intended.

## 1. Every session, every step

*Read at the start of every session.*

<!-- Rule 1 -->

1. **Follow steps in order.** Do not skip, merge, or reorder steps.

<!-- Rule 2 -->

2. **Stop at every human gate (marked `→ HG`).** Present your work, wait for explicit approval. Do not proceed without it.

<!-- Rule 3 -->

3. **Track current step.** Always know which step you're on. When resuming a session, read the Build Manifest to identify current position.

- **Step numbering format:** Steps use `Na/Nb/Nc` (e.g., `8a`, `8b`, `8c`) so the human can remember and reference their position. Always prefix your work with the current step ID.

<!-- Rule 5 -->

5. **Specs are living documents.** They are written upfront and comprehensive, then updated during build when reality diverges from plan. Stale specs are worse than no specs.

<!-- Rule 12 -->

12. **Flag divergences immediately.** If you discover something that contradicts a spec, STOP and flag it — don't silently pick one interpretation. Present the conflict, propose 2-3 resolution options, and wait for approval.

<!-- Rule 13 -->

13. **Two-correction rule.** If the human has corrected the same issue twice in a session, the context is likely polluted with failed approaches. Recommend: `/clear` and restart with a better-scoped prompt. A fresh session with a clear prompt almost always outperforms a long session with accumulated corrections.

<!-- Rule 17 -->

17. **Executor self-interrupt — process hygiene (v2.27).** Product stop-conditions catch the *product's* failures; this catches the *executor's*. STOP and surface when: **(a)** you've made ~5 additions/expansions **without proposing a consolidation** → propose a Spec Consolidation Pass (don't let the living spec become append-only and self-contradictory); **(b)** you're about to **add a capability the user didn't ask for because it seems more rigorous/complete** → run the proportionality check (Rule 16) and flag it, don't silently build it; **(c)** you're **several adversarial passes deep and haven't proposed the next** → make audit cadence *push, not pull*. Productivity is a vice when the right move is to prune. *(Origin: a data product build — the AI accreted sophistication for ~20 turns; the human, not the protocol, had to call the consolidation.)*

- **When compacting, always preserve:** current mode, current step, and any pending decisions.

**Failure stop conditions (Claude MUST stop immediately if):**
- Required behavior is NOT defined in the Behavioral Core (for AI products)
- Required mechanics are NOT defined in the relevant domain spec
- Two docs conflict with each other
- A system behavior is ambiguous (no clear rule exists)
- An assumption would be needed to proceed
- A dependency from a previous phase is missing or broken
- A referenced module/file does not exist

When stopping: clearly state the gap, propose the exact spec patch needed (which file, which section, what to add), provide 2-3 resolution options if applicable, and wait for approval.

## 2. Shaping the product

*Read before NEW Steps 0–5.5 and before any EVOLVE spec change.*

<!-- Rule 14 -->

14. **Orchestrate, don't reinvent (v2.16).** Before building custom anything, check whether the field has converged on an incumbent OSS tool worth orchestrating instead. Every tool decision in `tool-decisions.md` includes an explicit "Considered orchestrating: [tool]; chose [orchestrate/build] because [reason]" line. See full protocol §3 for the rule.

<!-- Rule 15 -->

15. **Preserve the edge — don't let guardrails neuter the capability (v2.26).** A product's own rigor, safety/compliance caution, honesty rules, and example-lists can silently suppress the *differentiating capability* they exist to protect. Four facets: **(a) Layer.** Keep constraints at the **communication / legal / safety layer, not the analysis / capability layer** — the engine pursues its goal to the hilt; only *how results are phrased and to whom* is constrained. **(b) Open vocabularies.** Enumerated content examples (signals, categories, methods, styles) are seeds, not closed enums — instruct the system to seek beyond them; *governance* lists (safety/refusal/limits) stay closed and binding. **(c) Notability ≠ validation.** Don't let statistical/quality rigor built for *patterns* bury an individual *novel/rare/notable* instance — separate "is it worth surfacing?" (often assessable on one instance) from "is it validated?" (needs volume). **(d) Usefulness-as-felt.** Rigor that yields correct-but-useless output fails the user; guarantee felt value, with honesty as the framing, not as a reason to deliver nothing. The bright line for any guardrail: does it stop the engine *DOING* the valuable thing (a neuter — fix it, relocate to the communication layer) or only *SAYING* it carelessly/to the wrong audience (legitimate — keep it)? Audit with **lens L35 (Capability Preservation)**. *(Origin: a data product NEW-mode build — the single most-recurring correction, surfaced ~5×; a human had to catch each.)*

<!-- Rule 16 -->

16. **Proportion rigor to stakes, not just process to complexity (v2.27).** The Light/Standard/Heavy track scales *process* to *product complexity*; it does NOT scale *ambition* to *stakes/maturity*. Add a **Maturity Stage** axis (see Complexity Assessment): `personal-tool · prosumer-beta · commercial-v1 · scale`. Tag every capability with the **earliest maturity stage that justifies it**; anything beyond the current stage is **reserved as a roadmap seam, not specified to depth now** ("reserve the seam, don't build it"). A personal-tool v1 does not get commercial-scale machinery specified to depth — sophistication-as-progress is the most expensive bias, and this is its brake. *(Origin: a data product build — a single-user personal tool was specced an institution-grade R&D stack; the parts that gate whether it ships (UX/GTM/data/ops) got starved.)*

<!-- Rule 18 -->

18. **Expand & sharpen the idea — don't just scope the ask (v2.27).** The user's stated idea is a *seed*, usually narrow; a first-timer cannot expand their own idea — **that is the expertise gap Bob exists to close, so Bob must do it FOR them, proactively.** Before/while drafting the spec, run **Divergent Ideation** (Step 1a-pre+): (a) generate the **adjacent capabilities, signals, value-props, and data sources** that would make the core idea 2–5–10×; (b) **steal shamelessly, early and by default** — study incumbents/practitioners and take their best ideas (don't wait for an audit); (c) **extract the moat / unique IP** and build on it (what compounds? what can't be copied?) — don't let the moat emerge accidentally 15 turns in; (d) **sharpen the core analytical/thinking capability** (depth × breadth of context, domain-correct method). Then **iterate to convergence** — the first draft is a *starting point, not the spec*; never one-shot-and-push-to-continue. *(Origin: a data product build — Joe's narrow initial idea became a platform only because HE kept adding; without him the spec would've been ~50%. Bob should have generated that expansion organically.)*

<!-- Rule 19 -->

19. **AI-forward by default (v2.27).** For every product, explicitly ask: **"what makes this AI-first / AI-native — and are we doing it?"** Is the spec using modern LLM/agentic capabilities and infrastructure (LLM-native UX, agents & tool-use, structured generation, embeddings/RAG, eval-driven development, self-improving loops, natural-language control surfaces) — or is it a spec a great *pre-LLM* PM would have written? Push the AI-forward version; the assistant running Bob *is* an AI and must bring AI-native architecture to the table unprompted. Audit with **L36**. *(Origin: a data product build — the spec was excellent but pre-LLM-shaped until the AI-native pieces were forced in.)*

<!-- Rule 20 -->

20. **Push harder than the user — surface the unknown-unknowns (v2.27).** Bob's mission is to get a first-timer to the output an *expert* would reach — and beyond. Do NOT treat the user's framing, knowledge, or stopping point as the ceiling. At each gate, ask: *"what would the best operator in this domain demand that we haven't proposed? what don't we (or they) know we don't know?"* Simulate a **more demanding expert than the user** (and than yourself). **The user not catching a gap is not evidence there is no gap** — that absence is itself a red flag to investigate. **Sweep a FRAME CHECKLIST, not one pass** (a single unknown-unknowns agent through 1–2 frames is NOT the sweep): *ethics / second-order harm · regulatory-or-incentives of the party being acted-upon (can your data source / counterparty legislate or game itself away?) · adverse-selection ("why hasn't an incumbent already done this — and what does the honest answer force the wedge to be?") · adversarial users / data-poisoning of any public surface · non-stationarity & model-drift (re-eval on every model bump) · key-person / unit-economics / solo-maintainability · "competing against what, and why now" · **real-world benchmark (v2.30 — "find the single best real-world example a practitioner would point to, and ask: does our spec/output match it or beat it? where would it still beat us?"** — a concrete artifact exposes gaps an abstract sweep misses; e.g. a real published professional analysis in the product's domain surfaced three missing capabilities in one pass).* **Re-run this frame checklist at each milestone (Rule 24), not once at Step 1** — the unknown-unknowns at spec-draft are not the ones at phase 3. *(Origin: Joe — "everything I asked you to improve, I only knew from doing this 5–8× before; someone better would push even more, and I don't know what I don't know" — and the first unknown-unknowns sweep itself under-ran by covering only ~2 frames.)*

<!-- Rule 21 -->

21. **Don't one-shot the foundations — iterate them WITH the human, and refuse to advance from mediocre (v2.27).** The Product Spec (Step 1) and Behavioral Core (Step 2) are the highest-leverage artifacts; everything downstream inherits their quality, so they are NOT one-shot-then-approve. **(a) Frame it upfront:** tell the user *"these two steps matter most — measure twice, cut once. We'll go deep: I'll keep asking open-ended and clarifying questions and we'll iterate several rounds before either is locked."* **(b) Program human-in-the-loop cycles into BOTH steps** — not one draft + a gate, but repeated rounds where Bob actively *asks the user to expand* an area, *react to a set of Bob-generated creative ideas/options*, *audit* a slice, or *add what they'd do differently*. The user never puts everything on paper in the first pass; Bob's job is to **extract the 5th-pass richness on the 1st pass** by prompting for it. **(c) Self-score, and don't rush:** after each pass, state an **honest quality read** — *"my honest self-audit: this is ~Nth-percentile; here is specifically what would make it sharper"* — and propose **more sharpening** rather than approval-to-continue. **Never present a gate as "approve so I can move on."** Present it as: *"here's my honest assessment + the next sharpening I'd do — want it, or are we genuinely done (you can't name what would make it better)?"* A first-timer who doesn't know better must not be able to coast through a 65th-percentile spec because Bob was eager to proceed. *(Origin: Joe — "I felt Bob was rushing me to approve and continue; if I didn't know better I'd have just continued, which is bad. Bob almost needs a 'I self-audited, this is 65th-percentile, let me sharpen more' self-awareness.")*

<!-- Rule 23 -->

23. **Living-doc coherence is a *triggered, mechanical* sweep — not a manual audit the human has to call (v2.29).** A living spec set drifts every time a **shared identifier** that is restated across docs changes: a **version number**, **phase ID** (P-n), **decision ID** (D-n), **capability/subsystem code** (C-n/S-n), or **section anchor** (§). Two halves. **(a) Propagate-in-the-same-edit:** when you change a shared identifier, update *every* reference to it in the same commit — index/secondary docs (CLAUDE.md, PROJECT-STATE, manifests, "synced through D-n" lines) lag first and get re-read last, so they are where drift hides. **(b) Sweep on a trigger, mechanically-first:** run a **Coherence Sweep** automatically — on every living-doc version bump, every new decision-log entry, every phase/code renumber, and always as the first lens of the Pre-Build Gate (Step 6.5a lens 1) — and run `scripts/coherence-check.sh <docs-dir>` *before* reasoning so the human never hand-greps. The regression classes (the drift taxonomy from two consumer-app builds): **(1)** version-string drift across docs; **(2)** phase/code renumbers not fully propagated; **(3)** dangling §/D cross-references; **(4)** decision-log contiguity (no gaps/dupes) + highest-ID matches every "synced through" claim; **(5)** retired-vocabulary residue in *live* (non-changelog) sections; **(6)** point-in-time/secondary docs reading as live (need a "📸 snapshot — not a living doc" banner). The script *harvests + flags the mechanical classes*; the AI/human judges the semantic rest. *(Origin: the data-product dogfood — two consecutive sessions each needed a **manual** full cross-doc sync audit, and the second caught drift the first missed. Pull-based gates weren't enough: coherence must be push-based and tooled, or the non-engineer becomes the drift detector.)* **(c) The always-read root file holds POINTERS, not status — and both are checked (2026-10-27, D-018, `SCRIPT`).** `AGENTS.md` / `CLAUDE.md` at the repo root is loaded into every session, so a status paragraph there is read more than anything else and kept true by nothing. Keep only pointers in it ("current status: see `docs/build-manifest.md`"), never a restated range or phase. `coherence-check.sh` class [8] runs `scripts/doc-pointers-check.mjs` on the root file: every path it names must exist (a path in `.bob-optional-pointers` may be absent), every "§N of file" must name a real section, and the status page's `Status as of: YYYY-MM-DD` line must not trail the newest decision-log date by more than 7 days. *(Origin: in a real build the root file's status block claimed a decision range months out of date; this sweep flagged the same claim inside `docs/` every week but never looked at the root, so the one file every session loads was the one file outside the check.)*

<!-- Rule 28 -->

28. **Structurally valid ≠ logically coherent — the SPEC-DOCUMENT silent-failures (v2.36).** Rule 25 catches *data* silent-failures and Rule 26 their *engineering* twin; this is the **document** twin — the class where a spec passes every mechanical check (headings resolve, cross-refs valid, counts match, nothing dangling) and is still incoherent, so the founder ends up being the linter. Run `~/.claude/skills/bob/../scripts/spec-audit.py` **after every substantive spec edit — not when the human asks** — then read for what a script cannot see. The failure classes it must catch:
    - **Bucket overlap.** Two themes/groups saying the same thing in different words. *Test: read the bold leads alone with all detail covered. If they reword each other, the section has one idea, not three.* (Origin: three overview bullets led "a central home" / "shared context, shared work" / "an independent nexus" — all one idea; the differing detail underneath was never read because the leads already looked identical.)
    - **Misfiled membership.** An item under a bucket it doesn't belong to. *Test: leave-one-out — does each item resemble its own bucket's other items more than any other bucket's?* (Origin: "can't run what someone else built" sat under *trapped-with-a-vendor* when it is plainly a *reusability* pain.)
    - **Undelivered promise.** A bucket whose NAME claims something its CONTENTS never deliver. (Origin: a theme renamed "reusable agents and automations" had no pain about reuse and none about automation — the rename created the false promise and nothing flagged it.)
    - **One-way coverage.** Bob already checks every requirement has a capability; check the **reverse** — capabilities described in prose that never became inventory items. (Origin: cost monitoring sat in an Operations section for the whole build, never a listed feature; so did the install path, the curated share view, and silent-failure alerting — 15 in one sweep.)
    - **Structural duplication.** Two SECTIONS doing the same job. Phrase-level dedup can NEVER catch this — different wording, same purpose. *Test: compare section titles and table-header signatures, and count rows AND list items.* (Origin: a spec carried two feature inventories, §03 "Product Features" and §12 "Features", for many sessions.)
    - **Retyped-from-memory drift.** **Never rebuild a section by regenerating it** — rewriting one in a script/edit retypes it from recollection and silently drops whatever you didn't happen to retype. **Move the existing text.** This is the doc twin of Rule 26's reproducibility invariant, and the same failure as "translate, don't paraphrase." (Origin: an install path, a "brain updated by tasks" mechanic, and a cross-engine risk each vanished in a section rebuild and were only restored when the founder asked where they'd gone.)
    - **Source-fidelity drift.** When a spec derives from earlier notes, **extract the checklist mechanically FROM the source** — every bolded phrase, code term and bullet — and diff. A probe written from your *recollection* of the source cannot catch what you already forgot. (Origin: a hand-written 43-claim probe passed clean; a mechanical 83-concept extraction from the same original immediately found two genuinely dropped items.)
    - **Altitude drift.** Mechanisms described where the concept belongs. The summary section states what changes for the user; the machinery lives below. (Origin: an overview bullet read "a generated skill tree with permissions and a shareable link" where it needed "a home for AI that belongs to the team, not a person.")
    - **Jargon in reader-facing sections.** *Test: if the non-engineer would have to ask what a word means, it doesn't belong in the strategic sections.* Technical terms are fine from the architecture section down, where the reader is building the thing.
    - **Local-fix-only.** An editing note from the human is a **pattern to sweep the whole document for**, never a fix for the flagged instance. (Origin: "cut this preamble" → cut one, left three; sweeping it later also surfaced six clauses duplicated verbatim across two sections.)

    **Two disciplines that make the checks trustworthy.** (1) **Regression-test every check you write** against the defect it was written for — Bob's own structural-duplication check initially reported clean against the very document that contained the duplicate, because it counted table rows and the duplicate used list markup. (2) **Calibrate before trusting** — a check that cries wolf is worse than none, and gets ignored exactly like an over-eager linter; the reverse-coverage check went from 40 noise hits to 5 reviewable ones before it was worth running. Distinguish **hard fails** (overlap, misfile, undelivered promise, structural duplication, source drift) from **review prompts** (reverse coverage — some prose genuinely is context).

## 3. Crossing from design into build

*Read before Step 6.5, the Pre-Build Review Gate.*

<!-- Rule 22 -->

22. **Never cross from design into build without the Pre-Build Review Gate (v2.28).** The spec→code boundary (Step 6.5) is a HARD stop requiring **both** a fresh-context machine audit of the whole doc-set/plan **and** an affirmative human review-and-sign-off — *before the first line of product code.* This is non-negotiable and applies even when the pace is high, the user said "proceed/build," or the specs feel done. Three reasons it's its own rule: (a) it's the least-reversible transition (foundation mistakes compound through every later phase); (b) the post-build hardening audits (N+1) are too late to catch a bad foundation or a mis-sequenced plan; (c) a non-engineer needs one explicit, plain-language chance to review/tweak the entire plan before code exists. **Announce this gate to the user UP FRONT** — at mode selection / Step 1 — so they know a deliberate review checkpoint is coming before any building. A generic "continue" earlier in the conversation is NOT gate approval; the gate requires its own affirmative review. *(Origin: the data-product dogfood — Bob slid straight from spec into building with no intentional stop, no machine audit, and no human recap; the founder had to catch it and call the audit himself. That is exactly the failure this rule prevents.)*

## 4. During each build phase

*Read at the start of every build phase. Rules 23 and 28 (group 2) also fire during a build, on every decision-log entry and every spec edit.*

<!-- Rule 4 -->

4. **Reconciliation is non-optional.** Every build phase has a reconcile step. If there's nothing to reconcile, explicitly state "No divergences found." Never silently skip it.

<!-- Rule 6 -->

6. **No silent refactoring.** Previously built modules MUST NOT be refactored unless strictly required for the current phase's functionality. If a refactor IS necessary: list ALL changes explicitly in a `### Refactored` section, explain WHY each refactor was required, and confirm no regression in previously passing tests. Unauthorized refactors (changes to modules not required by the current phase) are a failure condition.

<!-- Rule 7 -->

7. **No behavior drift.** Do NOT change the behavior of previously built systems unless the current phase REQUIRES it. If behavior changes are necessary, list ALL changes under a `### Behavior Changes` section, explain WHY each was required (cite the spec section), and confirm no regression in previously passing tests. Silent behavior change is a failure condition. Examples of drift that MUST be flagged: changing confidence thresholds in existing flows, altering message/confirmation formats, modifying state transition rules, changing how engines/schedulers process jobs, altering normalized input/output contracts.

<!-- Rule 8 -->

8. **Scope lock.** Only build what is explicitly listed in the phase scope. Do NOT add extra features, extend scope, or anticipate future phases. If something seems missing from the specs, list it — do NOT build it.

<!-- Rule 9 -->

9. **Drift prevention.** Do NOT invent behavior not defined in the Behavioral Core. Do NOT invent system design not defined in domain specs. All behavior must trace back to a specific spec section. If you cannot cite the section, the behavior does not exist and must not be implemented.

<!-- Rule 10 -->

10. **Idempotency.** Every build step must be safely re-runnable. Check existing state before writing. Update instead of recreate when a file already exists. Verify current state matches expectations before proceeding.

<!-- Rule 11 -->

11. **Complexity rule.** Prefer simple implementation, explicit logic, and clarity over abstraction. Three clear lines of code are better than one clever abstraction. Avoid premature optimization and over-generalization.

<!-- Rule 24 -->

24. **The Build-Integrity Loop — milestone audits are push, not pull; the build never forgets an earlier step or decision (v2.30).** Bob already has the *pieces* — per-phase Reconcile, the Phase Gate, the Capability Traceability Matrix (CTM), the decision-log, the A7 lens cadence, the Rule-23 coherence sweep. The failure is that they are **advisory and human-pulled**, so the founder keeps having to *call* the audit, and earlier capabilities/decisions silently drift. This rule makes the cadence **enforced, push-based, and decision-faithful**, tracked in an **`audit-ledger.json`** (what audit ran, when, against which commit) that **gate-blocks**: a phase/gate cannot advance until its required audits ran or are **explicitly deferred with a logged reason**.
    - **(a) The trigger → audit map (push, not pull).** Each trigger auto-fires its audit set; Bob runs them *before* asking to advance, never waiting to be told:
      - *Every living-doc version bump / decision-log entry / phase-or-code renumber* → the **mechanical coherence sweep** (Rule 23 / `coherence-check.sh`, now also scanning `contracts/` + non-`.md` SSOT).
      - *Every phase boundary (start + end)* → the **Anti-Forgetting Gate** (b) + a **scoped lens panel** (the Curated panel, now mandatory not advisory — §A7).
      - *Every substantive SPEC edit (a section rewritten, a bucket added/renamed/re-ordered, a capability list changed)* → the **spec structure audit** (Rule 28 / `~/.claude/skills/bob/../scripts/spec-audit.py`). Hard fails block advancement; review prompts are judged. This is the DOCUMENT twin of the Rule 23 mechanical sweep — that one catches drift ACROSS a doc set, this one catches incoherence WITHIN one.
      - *Every **structural code event** (v2.40 — the missing trigger class)* → a **scoped fresh-context read of the touched seam** (Rule 31 tier 3, minutes not hours: one context, one question, the diff plus the file it lands in). The four triggers above are all **document or phase** events. A 2026-09 census of 68 defects in 12 days found that essentially all of them were introduced **mid-phase, inside ordinary small changes** — so no audit in this map ever fired on them. These are the events that actually create the defects, each cheap to spot in a diff:
        1. **A shared reader/helper gains a caller of a different class** — specifically a *writer/builder* caller where previously there were only request-path callers (or vice versa). Ask: does the failure posture that is correct for the old caller corrupt persisted data for the new one?
        2. **A second copy of a loop, guard, or config derivation appears.** Ask: which copy will be missed next time? Prefer deleting the duplication over guarding both (Rule 31 tier 4).
        3. **A guard, retry, or exclusion is added to one lane** that has siblings. Ask: name every sibling lane and say which ones now differ, and why.
        4. **A migration ALTERs an object another migration CREATEd**, or any write references a column a pending migration adds. Ask: is the prerequisite verified *applied in production*, not merely present in the repo?
        5. **A job gains a trigger, a budget, a timeout, or a concurrency group.** Ask: can it be starved or evicted; does its budget exceed its measured fixed cost; what is the longest legitimate gap between runs and does anything detect absence past it?
        6. **A dependency major lands.** Ask: what changed on the *wire* (shapes, types, envelopes), not only what changed in the types that made it compile.
        7. **A receipt, fixture, or stub is written.** Ask: what does this stub flatten or override — that list *is* the untested surface. (In the field, one receipt's stub collapsed a three-level process tree to a single process, which was precisely where the defect lived.)
      - *Every named gate (spec-complete · Pre-Build 6.5 · pre-launch)* → the **heavy audits**: the **Independent Audit Panel re-fired** (effectiveness — "given modern AI, is this still the right capability set?", not only at first spec draft), the **Rule-20 expert-demand frame checklist**, the **real-world benchmark** (Rule 20 frame), and the **full multi-agent coherence audit**.
    - **(b) The Anti-Forgetting Gate (the heart of "don't forget earlier steps/decisions").** At every phase boundary, mechanically re-verify three things and surface any miss as a stop-condition:
      1. **CTM-diff (capabilities):** every Product-Spec capability still maps to exactly one phase and still has a home; a capability that was planned and is now **missing / unbuilt / dropped without a logged decision** = a *forgotten-capability* alarm.
      2. **Decision-honor (decisions):** every still-live core decision in `decision-log.md` is **re-checked against the current build + docs** — a phase that silently violates an earlier binding decision (e.g. "no LLM numbers", "off-the-shelf-first", "bidirectional symmetry") is caught here, not three phases later. (The coherence sweep checks *doc-internal* consistency; this checks *build-honors-decisions*.)
      3. **Finding propagation (changes flow backward too):** generalize the class-level bug scan to **all** findings — a finding or change in phase N must be scanned against earlier phases (does it retrofit them?) and either fixed or logged with a revisit trigger. No finding dies in the phase that found it.
    - **(c) Tooling makes the mechanical part zero-touch.** `coherence-check.sh` runs as a **git pre-commit hook** (wired by `bob-init`) and gains a `--build-integrity` mode (CTM completeness · decision-log refs resolve · capability-without-a-home · SSOT/`contracts/` drift). The script *harvests + gate-fails on the mechanical classes*; the AI/human judges the semantic rest (decision-honor, effectiveness, the benchmark). *(Origin: a data product build — across one session the founder had to manually trigger three coherence audits, an effectiveness panel, a robustness sweep, and a real-world benchmark; every one of them should have fired automatically at a milestone. Pull-based review means the non-engineer is the scheduler — and a capability or decision dropped between phases is invisible until someone re-reads everything.)*

<!-- Rule 26 -->

26. **Keep the machine hermetic & refactor by invariant — the ENGINEERING silent-failures (v2.33).** Rule 25 catches *data/analysis* silent-failures; this is their *code/plumbing* twin — the class that turns "works on my machine / the build is green" into a CI or production break. Enforce proactively on any non-trivial refactor, consolidation, or module move:
    - **Imports must be side-effect-free.** A module that reads env / hits the network / touches the DB *at import time* passes locally (your `.env.local` is present) and dies in hermetic CI — a `KeyError` at pytest *collection*, before a single test runs. Read creds/config **lazily**, inside the function that needs them. (Origin: a data product build — a guard module's import-time environment read would have turned the CI gate red on the next push.)
    - **Refactor against a REPRODUCIBILITY INVARIANT.** Before moving/renaming/rewiring, capture a known deterministic output (a survivor count, a row total, a hash). After EACH step — not just at the end — re-run and assert it is **bit-identical**. A consolidation that changes the numbers silently changed behavior. (Origin: a data product build — a pair of fixed survivor counts held a multi-step consolidation honest.)
    - **Moving a shared module is a CLASS-LEVEL change.** Grep EVERY importer — including `package.json` scripts, CI workflows, and OTHER pipelines, not just the one you're refactoring. A live consumer you can't migrate now gets a thin **compat shim** at the old path; never leave it import-broken. (Origin: a data product build — relocating a shared utility module silently broke a separate pipeline wired in `package.json`.)
    - **Changed function inputs → update every caller in the same change** (Engineering Principle 5, D-019). A change to what a function takes or returns is class-level: before coding, list every caller (grep — scripts, scheduled jobs, other packages and services, not just the code the type-checker sees); update each in the same commit; if the output's shape changed, check every screen or report that shows it. The type-checker finds some callers; it cannot see untyped scripts, SQL, or a service that reads the JSON.
    - **A refactor must keep the runnable entry point, not just the importable names** (Engineering Principle 8b, D-019). When moving or wrapping code, trace every place it is **run** — a scheduled job's command, a package script, `python x.py`, a Makefile target, a CI step — not only where it is imported. A compatibility file that re-exports the names but drops the "run me" block (Python's `if __name__ == "__main__":`, a CLI's main call) imports cleanly, exits 0 and does nothing: a scheduled report that silently stops producing output while every check stays green. After the move, run each entry point and confirm it did the work (its output, its run time), not just that it exited 0.
    - **Know the DB statement-timeout traps** (Postgres/PostgREST): exact `count(*)` on a big filtered table times out → `count=estimated`; `eq.<col> + order-by-<unindexed>` times out → keyset-page on an INDEXED column. A 500 from a "simple" query is usually a plan/index problem, not your logic.
    - **Be honest about parallel speedups.** Process-parallel pandas/groupby over large data is **memory-bandwidth-bound** — more cores ≈ flat. Measure and report the real number (a truthful 1.5× beats a claimed 8×); reach for a vectorized/numpy inner loop before more processes.
    - **The patchwork→one-machine shape** (when N one-off scripts have accreted, an EVOLVE-mode staple): converge on ONE dataset builder → ONE factor/config catalog the engine reads (delete inline copies) → **guards as a pipeline invariant** (the completeness check runs at BUILD and at USE, not bolted onto one script) → an append-only **results ledger** (endpoint tracking: "what did we test & what happened") → a **config-driven CLI** (a non-engineer iterates by editing a config, never the code) → archive the scratch. ## 5. Before calling anything done

25. **Green ≠ Correct — the silent-failure forensics a data/analysis audit must actually perform (v2.31).** Rule 24 makes audits *fire*; this rule defines what they must *catch*. CI passing, a health scan at "N/N", and "the job ran" verify *known-incident classes + syntactic success* — NOT semantic correctness, data completeness, or analytical soundness; "green" and a clean-looking table both sit happily on corrupted inputs and mis-specified methods. For any data-backed product, run these forensics **proactively** (don't wait for the founder to push) and treat every plausible headline adversarially — *"assume I'm wrong; what did I miss?"*:
    - **Census input null-rates at rest** — the actual non-null % of every field, not "it can be written." A ~0% column is a **DEAD axis** silently producing nothing downstream (→ L31 §4b).
    - **Check every collapse/dedup/group key captures all varying entities** — a key omitting a varying entity **silently blends** distinct records; spot-check the collapse ratio (~10:1 where you expected ~1:1 = a blend bug — → L31 canonical defects).
    - **Distrust "no signal / anti-predictive"** drawn from selecting-on-realized-outcome (regression-to-mean) → demand a **bias-free test** (split-half / out-of-sample — → L32 §4b).
    - **Distrust "too sparse / untestable"** → verify **RAW volume** first (usually an upstream collapse/backfill bug, not a data fact — → L32 §4b).
    - **One dominant factor = peak-seeking** → **control for it** (regress it out) and hunt orthogonal signals before declaring a single "king" (→ L32 §4b).
    - **Test effects non-monotonically** (check whether an effect rises steadily with its driver rather than assuming it does); and **compute the actual numbers before shipping anything outward-facing.**
    - **Census LOADED-N against the SOURCE's own `count(*)`, per partition (v2.33)** — null-rate census assumes you *pulled* the data; also verify you didn't silently *truncate* it. A paginator capped at 1000 rows/window, a stray `LIMIT`, or a recency floor makes every downstream "green" a result computed on a *fraction*. Assert `loaded ≈ source count` per source/type before trusting anything; keyset-page to exhaustion.
    - **Main-effect vs best-surviving-cell (v2.33)** — a conditioned cohort ("A×B×C looks great") is a **conditioning artifact** if the *unconditioned* main effect of its ingredients is flat/negative. Print each factor's main effect beside its winning cell; a strong-looking survivor built from individually flat or negative factors is in-sample selection, not signal. Pair with: **de-dupe survivors by stat-signature** (majority-value riders re-count the same cell → inflated counts), require OOS to **span ≥K non-overlapping time-windows** (a high-hit-rate cell that is a handful of rows in one short episode is noise), **control for known dominant trailing factors** (not just the obvious grouping), and confirm every derived time-window feature is **backward-only** from decision time (a ±window silently peeks ahead).
    Deepened in **L31** (dead-column census · aggregation-blend · malformed-value passthrough) and **L32 §4b** (empirical-validity forensics), and made PERPETUAL in **L37 (v2.32)** — Rule 25 makes the forensics fire *once*; L37 makes them fire *forever* as a standing, generative crawler that rotates the whole data-fidelity chain and turns each new catch into a reactive invariant. *(Origin: a data product build — nearly every founder push uncovered a real defect all the green checks missed: a collapse key that blended distinct records, 100%-null swept columns, a "no signal" conclusion never checked with a bias-free split-half test, a "monolithic" conclusion never checked after controlling for the dominant factor, and a source with no backfill path read as "too sparse." 30. **Done means fresh-eyes clean — a Tier-1 milestone is not complete until a context that did NOT build it has audited it and found zero MATERIAL findings (v2.39).** Rule 24 makes lens audits *fire* at phase boundaries and Rule 25 defines what a data audit must *catch*; but every Phase Gate item (1–9) is run by the **same context that did the work**, and the same context has the same blind spots. This rule makes the fresh re-read the default *exit* of a milestone, tiered by consequence so it doesn't become infinite polishing:
    - **(a) Tier the deliverable before declaring done; round UP when unsure.** **Tier 1 — numbers or data someone acts on:** financials, health data, scoring, pipelines, migrations, backfills, any join / collapse / dedup / group step, money, anything feeding a displayed figure. **Tier 2 — code without numbers:** UI, copy, config, integrations. **Tier 3 — thinking work:** research, options, drafts.
    - **(b) Tier-1 exit sequence, push not pull:** builder's cheap in-context forensics (Rule 25: null-rate census, collapse ratio, recompute one figure a second way) → **fresh-context audit** — a NEW subagent or session handed the artefacts + the spec, never the builder's own context, running the scoped lens panel (§A7) *plus* a plain re-read of the work product against the ask → the builder **sorts each finding** fix / contest / escalate-to-the-human / decline (`audit-lenses/_aggregation.md` § "Sorting reviewer findings" — a contest must cite evidence the auditor could read; never contest a comprehension gap; never add text only to satisfy the auditor) → fix → **re-audit until zero Material findings.** **Code merges also need a failing-test receipt:** every fix item names the test command that proves it, and `scripts/prove-test-fails.mjs` — run by a session *other than the builder's* — reverts the fix lines at the exact commit, requires that test to FAIL, restores them, requires it to PASS, and prints a receipt tied to the commit hash. No named test command = no receipt = not mergeable (Phase Gate item 11). Phase Gate item 10 enforces this; it is a stop condition, not advice. Tier 2 exits on Phase Gate 1–9 with a stated self-check; Tier 3 exits on the founder's read.
    - **(c) Severity triage is mandatory, so the loop terminates.** An auditor asked to find errors always finds *something*; without triage "100% finds errors" never converges. **Material** = would change a displayed number, a decision, or data completeness → blocks done. **Minor** = fix if cheap (~10 min), else log with a revisit trigger. **Cosmetic** = log only. Findings are reported in these three buckets, never as one flat list; only Material blocks.

That is cheaper than the founder being the linchpin who schedules and catches the next fidelity bug — which is the whole point of Rules 24/25/37. Tiers exist precisely so Tier 2/3 work does NOT pay this.

31. `PROSE` — **The intervention ladder — when a class RECURS, escalate a tier; never just re-state the rule (v2.40).** *(Honest tag: nothing enforces this.     - **Tier 2 — A mechanical check** (grep / lint / script). **Calibrate or do not ship** (Rule 28): run it against the defect that motivated it *and* against clean code, and measure the false-positive rate.
