# Project fit, pain recall and product angle

## Ground relevance

Start from the user's reason for sending the tool; infer reasonable focus rather than force an interview. Read the relevant current project purpose/status/handoff and actual input→output path. Inspect our equivalent before “you already have it,” “ours is better” or “no need.” Existing ownership is not superiority; installations/activity are not actual use/priority. Verify host capabilities and respect privacy zones.

Use project knowledge to widen discovery, not limit it: an unrelated tool may contain a useful interaction, architecture, review method or product framing. Separate current needs, plausible adjacent applications and unknown context. Every strong opportunity states observed current behavior (or explicit unknown), concrete improvement, adaptation burden, destination, next action and prerequisite.

## Current work, reusable capability and future projects

For each tool, consider current projects/workflow, a capability reusable across projects, and a concrete future product it could enable. These are discovery lenses, not quotas: record an evidence-backed opportunity or say why none was established. Read relevant existing idea/roadmap sources when available; do not invent the user’s plans or create another project registry. An unknown destination is valid, but is different from a deliberate future hypothesis.

Useful opportunities use application_type current/reusable/future. For future, future_scenario names the user, task and what this source enables; separate that hypothesis from demonstrated demand. Preserve source specifics even without a current destination. recommendation_timing distinguishes act-now from preserve/defer. A concrete revisit_trigger says when to reopen a preserved/deferred opportunity (a named project need, decision or dated check), not “if it matters.” These fields describe usefulness and priority; they never authorize integration.

Before recommending action now, compare the gain with keeping the current approach. Consider switching, adaptation and ongoing support/exit burden where relevant, without inventing ROI numbers or another score. Good source worth preserving need not be the next use of the user’s attention.

## Prioritize actions against active work

When the user asks what to action, first reopen current project priorities and evidence of frequently used workflows; commit activity or installation alone is not use. Search the full opportunity set, including reusable/future parts, rather than filtering only application_type=current. For each shortlisted action, connect a remaining gap to a current project objective or recurring workflow and explain its consequence and benefit. Rank that impact before convenience or small implementation effort; effort informs the choice but does not establish relevance. If a major active project is absent, explain whether no useful match was established or its context remains unknown. Keep speculative future opportunities separate; do not manufacture an action for every project.

## Sourced pain observations

Recall project_context.pains from generated component-index views and relevant historical records. For a potentially relevant pain, reopen the canonical project/user source and check whether it still applies. Source project documents remain authoritative; evaluation records are dated evidence snapshots, not a rival project database. No unrelated project document writes are implied.

Each observation records project, stable pain ID, problem, basis (user-stated/observed/inferred), source, observed_on (source date or unknown), and status (open/resolved/unknown). checked_on belongs to the evaluation snapshot; do not invent a source date from today's date. Only user-stated (or the legacy joe-stated alias) may be described as something the user reported experiencing; observed means a demonstrated issue, inferred means a hypothesis. A source must support the claimed basis.

Keep resolved pain as history, not an urgent open need. Reopen only with evidence of recurrence. Preserve differing project/ID/source observations and conflicting statuses; do not silently choose the newest-looking one or merge similar descriptions. Record missing sources/context as limitations; no memory of all conversations is promised. Capture new relevant pains/corrections in the evaluation, with pointers to their source; never manufacture a complaint to justify a tool.

## Product positioning and angle

For every tool, explicitly consider its intended audience, job/pain, problem framing, entry use case, packaging and value promise. A developer utility has a product angle too. Use README/docs, public product copy, examples and observed behavior as evidence; code alone may not reveal the intended angle.

Distinguish:
- **Claimed angle:** who it says it helps and how.
- **Delivered behavior:** what inspected implementation or observed interaction supports; unknown remains unknown.
- **Useful application:** what the user could learn for current work, a reusable capability or a concrete future product scenario, with a before/after and next test.

An ordinary implementation can have a useful framing; a compelling promise can lack working code. Don't infer demand, differentiation or effectiveness from copy, branding or popularity. User feedback remains an independent qualitative assessment. Propose useful angles as normal component opportunities (kind: positioning), with source evidence; don't create another score or require a separate long report. Copying public messaging/assets still needs permission/attribution checks, and publishing remains separately authorized.

## Re-evaluation

Record checked_on and prior date/revision when known. Compare prior and current source behavior, relevant product angle, project needs/pain status, blockers and copied-source/destination changes. State what changed and whether it changes the decision. If old source/date is unavailable, say so rather than fabricate a comparison. Fresh evidence can reverse an old call; don't preserve a rating for consistency.
