# Independent qualitative assessment

Assess the overall impression of the product/approach and experiences described by real users. Search current GitHub issues/discussions, user writeups, practitioner forums, migration accounts and relevant app reviews. Read underlying reports. Separate firsthand accounts, secondhand commentary, vendor statements and interpretation. Include dates/version/use case when material. Sponsored demos are not independent validation; one complaint is not prevalence.

Summarize what people accomplish, praise, specific complaints, workarounds/maintainer responses and contradictions. Include adoption, age, author concentration, funding or hype only when informative. Sparse discussion means limited feedback, not poor code or danger. No minimum review/popularity count; a star spike does not establish fraud or malicious code.

Reach a conclusion using its own evidence. It may differ from code usefulness and security. You may cross-reference those findings, but do not recast them as user consensus or use sentiment to establish implementation quality. Reviews can trigger source investigation; only independently inspected evidence changes code findings. Changing reputation alone must not change code findings. No combined score.

Optional stars for existing record/public columns: 5 strongly favorable impression; 4 favorable with named caveats; 3 mixed; 2 unfavorable; 1 strongly unfavorable. Use “not rated” with insufficient evidence. These stars do not set adoption or component value. Existing ratings had a mixed rubric; preserve them as historical, label rating_basis: legacy-mixed, and don't compare them as the same measure. New ratings use rating_basis: qualitative.

Maintenance may affect reliance on an external service or future releases: name the dependency and consequence in adoption tradeoffs. It does not make a self-contained copied function worse. Reported security incidents remain allegations until corroborated in security review.
