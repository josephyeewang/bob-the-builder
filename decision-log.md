# Decision Log

> ADR-format decisions for Bob the Builder itself. Format per `templates/decision-log-entry.md`. Decisions are recorded once and not re-litigated — this is the audit-resistant memory of intentional non-goals and load-bearing tradeoffs.

The companion `audit-log.md` records *deferred* items (Defer verdicts that may still ship later). This file records *Reject* verdicts (intentional non-goals that should NOT be re-evaluated absent a fundamental shift in context).

### D-001: Bob does not adopt influence patterns from Plandex / Roo Code / goose / Continue.dev

- **Date:** 2026-05-20
- **Status:** Accepted
- **Context:** v2.13 audit finding F13 (A7f Capability Gap, fresh competitor scan). v2.11's scan covered Spec Kit, Cursor rules, BMad, Aider, and Cline. The v2.13 re-scan surfaced four entrants worth at least listing: **Plandex** (persistent structured plans), **Roo Code** (Cline fork with custom modes — closest architectural parallel to Bob's NEW/AUDIT/EVOLVE pattern), **goose** (Block's agent runtime with session checkpoints), **Continue.dev** (context-prep + chat extension).
- **Decision:** We will NOT incorporate features or framings from these tools into Bob v2.13. None of them change Bob's "right thing to build" decisions for its target user (a non-engineer product leader building real products with Claude Code).
- **Alternatives considered:**
  - *Adopt Roo Code's custom-modes pattern as inspiration for additional Bob modes.* Rejected — Bob's three modes (NEW / AUDIT / EVOLVE) carry methodology weight, not just prompt scaffolds. Adding modes for the sake of variety would dilute, not deepen.
  - *Adopt Plandex's persistent structured plans.* Rejected — Bob's Build Manifest + Phase Reports already capture what plans capture, with more context (decisions, deviations, rollback).
  - *Adopt goose's session checkpoints.* Rejected — Bob's Pulse Report + handoff notes pattern (see Joe's CLAUDE.md multi-machine model) already cover this for the target user.
- **Consequences:**
  - We accept that Bob will not be the "most feature-rich" agent-protocol product in any single dimension. Bob's competitive differentiation is the **methodology depth** (5-doc hierarchy + audit modes + non-engineer narration) — not feature parity.
  - If a future audit pass surfaces a *specific* pattern from one of these tools that addresses a *specific* gap Bob can't solve another way, that ADR should reference this one as the supersession baseline.
- **Revisit trigger:** Any one of these tools ships an *external-fit-style audit step* (the closest competitor to Bob's A7f–A7h). That would be a genuine architectural overlap worth re-evaluating.
- **2026-05-20 addendum (v2.16):** The original Reject was scoped to **strategic positioning** — *should Bob's identity become like theirs?* — and that verdict stands unchanged. The v2.16 EVOLVE pass introduced a distinct sub-audit (A7f-implementation) that asks a different question: *are there specific MECHANISMS in those Rejected tools worth borrowing as discrete patterns?* The first run of A7f-implementation on the same 9 tools produced 3 mechanism-level Adopts (per-feature folder, plan-mode hard gate, sharded rules files) — see audit-log v2.16 entry. **Strategic Reject ≠ mechanism Reject.** This ADR's identity-level verdict is unchanged; future audits should use A7f-implementation for the mechanism question and not re-litigate the identity question logged here.

### D-002: Bob does not maintain a full Capability Traceability Matrix for itself

- **Date:** 2026-05-20
- **Status:** Accepted
- **Context:** v2.13 audit finding F23. Bob mandates a CTM in Step 5a-ii for any code product, and the v2.13 audit flagged that Bob (a markdown methodology product + 3 shell scripts) doesn't have one for itself. The mirror question was raised: should Bob eat its own dog food here?
- **Decision:** We will NOT maintain a full CTM for Bob itself. The CTM exists to prevent capabilities silently falling between specs and code in a multi-subsystem product. Bob has no subsystems in that sense — the protocol is a single document, the scripts are tiny and exhaustively grep-able, and there is no "Phase N" build cadence to map capabilities into.
- **Alternatives considered:**
  - *Build a minimal CTM mapping Bob's modes (NEW/AUDIT/EVOLVE) and major sections to the markdown anchors that define them.* Rejected — this would be a list of headings, not capability-traceability. The cost (maintenance) exceeds the value (none — nothing is at risk of falling through).
  - *Build a CTM only for the scripts.* Rejected — three scripts × ~100 lines each is below the threshold where CTM helps.
- **Consequences:**
  - The deferred-item register lives in `audit-log.md` rather than as a CTM column. That's the lightweight equivalent appropriate to Bob's shape.
  - We accept the slight inconsistency of Bob mandating-but-not-having a CTM. The protocol prose at Step 5a-ii now references `templates/capability-traceability-matrix.md` and the template explicitly addresses *code products* — readers of the protocol applying it to a methodology product would self-route to "skip per Light track."
  - The Light track in the Complexity Assessment already permits skipping the CTM for `<3` subsystems. Bob is comfortably below that threshold.
- **Revisit trigger:** Bob grows to multiple subsystems (e.g., a hosted dashboard, a telemetry pipeline, a marketplace of community-contributed templates). At that point, CTM becomes load-bearing.

### D-003: A7j Liveness Audit orchestrates incumbent OSS tools instead of building custom

- **Date:** 2026-05-20
- **Status:** Accepted
- **Context:** v2.14 added A7j Liveness Audit to catch silently-broken runtime code (functions that pass static review but throw on first invocation). The natural temptation was to build a custom liveness runner inside Bob — a Bob-flavored test harness, a Bob-flavored route enumerator, a Bob-flavored AI smoke checker. The alternative is to point A7j at well-established OSS tools with mature CLI + JSON-reporter interfaces and let Bob orchestrate them.
- **Decision:** A7j orchestrates incumbents. Bob does not implement any of:
  - Dead-code detection (use **Knip** for JS/TS, **Vulture** + **Ruff** + **deptry** for Python)
  - HTTP endpoint fuzzing from a schema (use **Schemathesis**)
  - Browser flow smoke (use **Playwright**)
  - Function-level smoke harness (use **Vitest** / **pytest**)
  - LLM surface smoke (use **promptfoo**)
- **Alternatives considered:**
  - *Build a custom Bob liveness CLI that abstracts all five tools behind one interface.* Rejected — the abstraction would lag the underlying tools (Knip ships a new release every few weeks; Bob can't keep up), be a maintenance tax with no proportionate value, and create a "Bob lock-in" feel that contradicts Bob's stance as a methodology, not a tool.
  - *Build only the orchestration layer (a script that runs all five tools and merges JSON outputs).* Considered — eventually appropriate, but not in v2.14. The protocol prose tells Claude exactly which tool to invoke and how; that's enough orchestration for now. Revisit if external users self-report this as friction.
  - *Pick one tool per stack and require it.* Rejected — different projects already have different tools wired up; Bob should adapt to what the user has, not impose a particular vendor.
- **Consequences:**
  - A7j's quality is bounded above by the quality of the underlying OSS tools. When Knip improves, Bob improves for free. When (e.g.) Schemathesis drops support for a spec format, A7j inherits the limitation.
  - The protocol prose at [N+1]j must keep tool recommendations current. If one of the cited tools dies (as ts-prune did before v2.14), the protocol needs an audit pass to update.
  - Users running A7j must install the relevant tools first. The protocol could add a one-shot installer script as future work; deferred (audit-log F27).
  - Bob's "do not reinvent" principle is now explicit in a decision, not just an implicit norm. Future audits proposing custom tooling for similar problems should reference this ADR.
- **Revisit trigger:** Either (a) one of the cited incumbents becomes unmaintained without a clear successor, OR (b) multiple PR-back reports cite tool-orchestration friction as the biggest A7j pain point.

### D-004: Bob projects use a single rules file (CLAUDE.md), not sharded rules with glob-scoped activation

- **Amended by D-025 (2026-10-28):** the one file is now `AGENTS.md`; `CLAUDE.md` only imports it.

- **Date:** 2026-05-20
- **Status:** Accepted
- **Context:** v2.16 dogfood pass (A7f-implementation scan) flagged sharded rules files with YAML frontmatter scoping (Cursor `.cursor/rules/*.mdc`, Continue `.prompt`, Cline `.clinerules`, Roo `.roomodes`, goose `.goosehints`, BMad templates) as the **strongest single Adopt** in the entire run — 5 of 9 tools converged on this exact mechanism. Initially deferred as F35 pending a discrete EVOLVE pass. On user review, Joe rejected the premise: *"not sure why anyone would deviate from a single rules file."*
- **Decision:** Bob projects keep a **single CLAUDE.md** as the agent's rules surface. We will NOT shard into `.claude/rules/*.md` with glob-scoped activation, even though tool convergence suggests it.
- **Alternatives considered:**
  - *Mirror Cursor's `.cursor/rules/*.mdc` shape with `description` + `globs` + `alwaysApply` frontmatter.* Rejected — the sharded model assumes a project large enough that monolithic rules pollute context; Bob's target user (non-engineer product leader) ships single-purpose products where a slim CLAUDE.md (the protocol already mandates <150 lines) fits comfortably as always-on context. Splitting it adds cognitive overhead (where does this rule go?) without proportionate benefit.
  - *Document a Bob-flavored sharding convention.* Rejected — would violate D-003 ("orchestrate, don't reinvent") because the underlying tool (Claude Code) doesn't have native scoped-rule machinery in the same shape, so we'd be inventing a Bob-specific format.
  - *Wait until projects accumulate enough rules that CLAUDE.md becomes painful.* Rejected as the trigger — by then we'd be migrating a convention rather than designing one. If pain ever shows up, the response is "prune CLAUDE.md," not "shard it."
- **Consequences:**
  - The dogfood meta-finding gets a stronger anchor: **convergence across tools ≠ Adopt for Bob.** F35 is now the canonical example — a mechanism that 5 of 9 tools share, that Bob still rejects because the target user is different. Future scans surfacing convergence-Adopts should reference D-004 as the reminder that field convergence is signal, not verdict.
  - The "single rules file" stance is now load-bearing for Bob's design. Step 6a's CLAUDE.md template stays monolithic; the <150-line elimination test ("Would Claude make a mistake without this?") becomes the maintenance discipline rather than sharding.
  - We accept that Bob projects with unusually large rule sets *may* eventually want sharding — but at that point the project has already outgrown Bob's target shape, and the right answer is to question the rule-set growth, not to add sharding ergonomics.
- **Revisit trigger:** A Bob user reports that their CLAUDE.md exceeded 300 lines without obvious prunable content, and the rule bloat is materially hurting their session quality. Until then, this is the Bob position.

### D-005: The Lens Retro loop surfaces lens edits — it never commits them. Bob does not auto-edit its own lenses.

- **Date:** 2026-05-25
- **Status:** Accepted
- **Context:** v2.18 added the Audit Self-Learning Loop (auto-emitted lens retros + `scripts/lens-retro.sh` aggregation). The obvious next step — and the one Joe explicitly raised as a possibility — is *full* automation: Bob reads accumulated retros and rewrites its own lens prompts without a human in the loop. The retro JSONs are structured; an agent could mechanically apply the highest-frequency change-requests. Joe asked for the semi-automatic version (auto-emit + flag) and we deliberately stopped there.
- **Decision:** Bob's lens-retro loop is **surface-only**. `scripts/lens-retro.sh` flags review candidates; Bob proposes specific edits; a **human supplies the verdict**; approved edits go through a normal EVOLVE + F47 dogfood. Bob will NOT auto-edit, auto-merge, or auto-ship changes to its own lens prompts from retro signal.
- **Alternatives considered:**
  - *Auto-apply change-requests above a frequency threshold (e.g., "3+ retros agree → edit the lens").* Rejected — this is precisely the D-004 / F35 failure mode. In v2.16, 5 of 9 surveyed tools converged on sharded rules files (the single strongest mechanical signal in the whole scan); Joe correctly rejected it anyway on higher-order judgment. **Convergence across sources is signal, not a verdict.** An auto-apply rule would have shipped F35. The human filter is the load-bearing part, not the aggregation.
  - *Auto-draft a PR that a human merges.* Considered, deferred — closer to acceptable because a merge gate preserves the human verdict, but it adds CI/PR machinery that contradicts Bob's prose-driven, low-infrastructure stance (D-003) and isn't worth it until retro volume is high. Revisit if retro volume ever justifies it.
  - *Convergence-to-mediocrity risk.* Lens prompts are load-bearing (~7,200 lines of curated content synthesized from 46+ sources). Auto-editing toward whatever the average retro complains about would sand off the distinctive lenses (L01 Liveness, L02 Spec Fidelity, L03 Critical Capability Quality, L28 Wedge) precisely because they're unusual — the same anti-convergence logic L28 applies to product features applies to Bob's own lenses.
- **Consequences:**
  - The loop's improvement cadence is gated on a human running the ritual (`_lens-retro.md` §B). That is intentional friction, not a missing feature.
  - Retros accumulate even when nobody acts on them, so signal isn't lost between rituals — the cost of the human gate is latency, not data loss.
  - If a future contributor proposes "let Bob improve its own lenses automatically," this ADR is the answer: surface, yes; commit, no.
- **Revisit trigger:** Retro volume grows large enough (e.g., dozens per quarter from external users) that human triage becomes the bottleneck AND a PR-with-human-merge-gate is built. Even then, the human merge verdict is non-negotiable — only the *drafting* would automate.

### D-006: From the Spec Kit `/clarify` scan, Bob adopts the coverage taxonomy only — not ID-traceability or CLI machinery

- **Date:** 2026-06-16
- **Status:** Accepted
- **Context:** v2.25 (evolution 003) harvested GitHub Spec Kit's `/clarify` command after a Bob-vs-Spec-Kit deep comparison. `/clarify` bundles four mechanisms: (1) a fixed ambiguity taxonomy, (2) capped recommended-default questioning, (3) incremental write-back, and (4) — via the sibling `/analyze` command — stable `FR-###`/`SC-###` requirement IDs mapped to tasks for zero-coverage detection. Spec Kit also ships a `specify` CLI with self-upgrade and a YAML extension-hook system.
- **Decision:** Bob adopts mechanisms (1)–(3) into Step 1b (the Coverage Taxonomy + capped resolution + write-back to existing artifacts). Bob does **NOT** adopt: the FR/SC ID-traceability + task-coverage map, nor any CLI / extension-hook / self-upgrade machinery.
- **Alternatives considered:**
  - *Adopt FR-###/SC-### IDs with a task-coverage map.* Rejected — Bob already covers requirement→phase→test traceability via `templates/capability-traceability-matrix.md` (Step 5a), the L02 Spec-Fidelity lens, and mandatory Reconciliation. Adding a parallel ID scheme in Step 1b would be two sources of truth for the same concept — a direct Single-Source-of-Truth violation and exactly the kind of sprawl the v2.17 meta-finding warns against.
  - *Adopt the `specify`-style CLI + extension hooks.* Rejected — this is **distribution machinery, not methodology**. Bob is a prose-driven Claude Code skill for one non-engineer; a versioned CLI with pluggable YAML hooks solves a multi-agent-portability / community-contribution problem Bob doesn't have. This is the same call as F35 (sharded rules, D-004): the mechanism scan can surface it, the human still rejects it.
- **Consequences:**
  - Step 1b gains a coverage *checklist* but not a coverage *ledger* — there is no machine-checkable "every requirement has a task" gate at spec time. That gate lives later (Step 5a matrix + Reconciliation), by design. If a future project shows requirements silently dropping between spec and build *despite* the matrix, revisit whether ID-tagging at Step 1b would help — but only as a supersession of this ADR, not a quiet addition.
  - Bob stays CLI-free and low-infrastructure (consistent with D-003). If Bob is ever productized for external users (the "Bob as a public tool" question), Spec Kit's CLI/extension model is the documented blueprint to revisit — but that is a strategic decision outside any single evolution.
- **Revisit trigger:** (a) requirements demonstrably leak between spec and build despite the Step 5a matrix; or (b) a deliberate decision to make Bob a public, multi-agent-portable product.

### D-007: "Done" is tiered by consequence; Tier-1 work exits only on a fresh-context audit with zero Material findings

- **Date:** 2026-09-13
- **Status:** Accepted
- **Context:** Across a data product and other data-heavy work the founder observed that every post-milestone audit he *requested* found real errors — 100% of the time — and had begun hand-instructing every project to audit every milestone. Rule 24 (v2.30) already made lens audits fire at phase boundaries and Rule 25 (v2.31) defined the silent-failure forensics, but every Phase Gate item was executed by the context that built the work; the fresh re-read — the mechanism that actually finds the defects — remained pull-based. Meanwhile, "audit everything" has no stop condition: an auditor asked to find errors always finds something.
- **Decision:** Rule 30 + Phase Gate item 10. Every deliverable is tiered (1 = numbers/data someone acts on; 2 = code without numbers; 3 = thinking work). Tier 1 exits only after a fresh-context auditor (new subagent/session, never the builder) reports zero **Material** findings; findings are always triaged Material / Minor / Cosmetic; `audit-ledger.json` records counts per audit. Tier demotion is *proposed* after five consecutive zero-Material audits on a class of work — never auto-applied (consistent with D-005). Mirrored as a plain-language "Definition of done" rule in the founder's global CLAUDE.md so non-Bob work inherits it.
- **Alternatives considered:**
  - *Blanket "always audit every milestone."* Rejected — no stop condition, doubles cost on research/drafts where it buys nothing, and the founder would abandon it within weeks.
  - *Enforce via a Stop hook that asks "which tier? has the fresh audit run?" on every task end.* Deferred — guarantees the question is asked but adds a line of noise to every trivial task; revisit if Rule 30 is observed to be skipped in practice (the ledger will show it).
  - *Make the builder's self-audit stricter instead of adding a fresh context.* Rejected — same context, same blind spots; the 100% find rate came specifically from fresh reads.
- **Consequences:**
  - Tier-1 milestones cost ~1.5–2× in tokens/time. Accepted deliberately: cheaper than the founder as scheduler + linchpin.
  - `audit-ledger.json` gains a per-audit severity record; `bob-init`/`coherence-check.sh --build-integrity` should learn to gate on item 10 (not yet implemented — Rule 30 is currently enforced by protocol prose, like Rule 25 was before L37).
  - Tier boundaries will be wrong at first. The ledger is the correction mechanism; the founder should expect 1–2 tier reassignments per project in the first month.
- **Revisit trigger:** (a) the ledger shows Tier-1 audits being skipped or Material findings routinely reclassified as Minor to unblock — then adopt the Stop-hook alternative; (b) three projects in a row show zero Material findings across all Tier-1 classes — the tiers are too broad, tighten Tier 1; (c) Material findings keep appearing on Tier-2 work — a class is mis-tiered, promote it.

### D-008: Green ≠ Correct — the silent-failure forensics a data/analysis audit must perform (Rule 25 / L31 + L32)

- **Date:** 2026-07-22
- **Status:** Accepted (v2.31)
- **Context:** The direct sequel to D-024. Rule 24 made Bob's audits **fire** automatically at milestones — but an audit that fires without knowing *what to look for* still misses defects. Across a run of data-product sessions, nearly **every** improvement was surfaced by a founder *push-back on a plausible-looking result*, and each push uncovered a real defect that CI (green), the data-health scan (all checks passing), and "the analysis ran successfully" all reported as healthy: a **collapse key that omitted a varying entity** blended many distinct records into one arbitrary row and corrupted every downstream stat; **two analysis columns were 100%/near-100% NULL** (dead swept axes producing silent nothing); a **"no signal" conclusion** had never been checked against a bias-free split-half test (a null drawn from selecting on outcomes can be a regression-to-the-mean artifact); a **"findings are monolithic"** conclusion had never controlled for the dominant factor before re-ranking (ranking by effect size can restate one factor N times); and a **"too sparse to test"** conclusion had never verified raw volume against the source (an un-backfilled source can masquerade as sparsity). Joe: *"I don't want to always be the linchpin to catch these — consolidate the learnings so the system catches them."* The gap: "green + it ran + a clean table" verifies *known-incident classes + syntactic success*, never semantic correctness, data completeness, or analytical soundness.
- **Decision:** Add **Rule 25 — Green ≠ Correct** (cross-cutting; the *what-to-catch* complement to Rule 24's *when-to-fire*), and deepen the two lenses that own the surfaces. **L31 (Input & Data-Flow Trace)** gains an at-rest **null-rate census** (step 4b — a ~0% column is a dead axis, not "it can be written"), and two canonical flow defects — **aggregation-key blend** (a collapse/dedup/group key omitting a varying entity silently merges records; spot-check the collapse ratio) and **malformed-value passthrough** (e.g. an identifier of one kind leaking into a column meant for another, silently breaking a downstream join). **L32 (Analytical Method Soundness)** gains **§4b Empirical-Validity Forensics**: selection-on-outcome false-nulls (→ split-half / out-of-sample), peak-seeking false-"monolithic" (→ control for the dominant factor, then re-rank), sparse≠untestable (→ verify raw volume for an upstream collapse/backfill bug), and non-monotonic effects (test whether an effect rises steadily with its driver rather than assuming it does) — plus finding categories + an anti-pattern. The stance runs **proactively** (don't wait for the founder to push) and treats every headline adversarially. **No new lens** (deepens L31/L32); rules → 25; lens library unchanged at 36. Wired across `build-protocol(-core).md`, `CLAUDE.md`, `_execution-principle.md`, `skill/SKILL.md`, both READMEs; recorded under `evolutions/004-silent-failure-audit/`.

### D-009: Perpetual Data-Fidelity Crawler — make the silent-failure forensics STANDING + generative (L37)

- **Date:** 2026-07-23
- **Status:** Accepted (v2.32)
- **Context:** The direct sequel to D-008. Rule 25 defined *what* a data/analysis audit must catch and deepened L31/L32 to catch it — but it still **fires once per audit**, and the data-product recurrence continued: a single session alone surfaced a **unit change that was never normalized** (with the sanity check skipping that input and a unit test encoding the wrong assumption), a **silent row cap** on a data read, **records labeled before the labeling logic shipped**, and **scans that outgrew a timeout and hard-failed scheduled jobs** — every one green until a human or a fresh audit found it. Root cause: the existing defense (a registry of named data-quality invariants) is **reactive by construction** — each invariant encodes a bug that *already* bit, so it can never catch the *next* class; meanwhile the data surface (fields/sources/joins/collapses/derivations/served reads) grows monotonically, leaving every new edge unmonitored. The human remained the **generative hypothesis source** ("wait, that can't be right"). Joe: *"why do we keep having fidelity/extraction/interpretation/linkage issues — design an audit that catches these AND goes beyond, that I can run continually so it crawls for new angles."*
- **Decision:** Add **L37 — Perpetual Data-Fidelity Crawler** (Band 1) + companion **`audit-lenses/_data-fidelity-chain.md`** (the 7-stage chain SOURCE→EXTRACT→INTERPRET→LINK→COLLAPSE→OUTCOME→SERVE, the 7-mode × stage failure taxonomy, and a **13-oracle catalog**). Split the problem into **memory vs imagination**: the reactive registry is memory (replay known failures every commit — keep it); L37 is imagination — a **STANDING, scheduled, generative** crawler that reads a coverage ledger, rotates to an un-crawled slice, **generates a falsifiable fidelity hypothesis per cell**, and **tests it against an INDEPENDENT oracle** (total↔Σ(parts), implied-value band, null-rate census, collapse-ratio, coverage-depth vs source truth, cross-source reconciliation, extraction-completeness diff, distribution drift, code-vs-data temporal consistency, selection-bias re-test, pseudo-replication clustering, served↔computed, row-count conservation). The oracle-selection heuristic prefers the truth-source *most independent* of the pipeline (recompute-from-parts / an external reference value / the source's own counts beat any same-codebase range assert — the kind that already missed). **Self-learning (imagination → memory):** each confirmed defect auto-**drafts** a new reactive invariant for the registry + a lens retro. **Boundary honored (D-005):** it drafts; the human merges — Bob never auto-edits its own lenses. Rules unchanged; **lens library 36 → 37.** Wired across `skill/SKILL.md`, `build-protocol(-core).md`; recorded here. *(Note: L37's value is as a perpetual scheduled job — run it via the project's Cron→queue→worker lane, not only as a one-shot pre-launch pass.)*

### D-010: Keep the machine hermetic & refactor by invariant — the ENGINEERING silent-failures (Rule 26)

- **Date:** 2026-08-04
- **Status:** Accepted (v2.33)
- **Context:** The code/plumbing sequel to D-008/D-009. Those made Bob catch *data/analysis* silent-failures; a later run of data-product sessions showed an equally recurring *engineering* class that "the build is green / works on my machine" hides — surfaced repeatedly across one large consolidation (many accreted one-off analysis scripts → one guarded machine): (1) a data pull that **silently truncated** — a paginator capped at a fixed rows-per-window limit ran every recent analysis on **a fraction of the events**, green the whole way, because the census checked null-rates but never *loaded-N vs the source's own count(\*)*; (2) a guard module that read a database credential from the environment **at import time** — fine locally (`.env.local` present), a `KeyError` at hermetic-CI **test collection** on the next push; (3) moving a shared utility module **silently broke a separate pipeline** wired in `package.json` (the move was treated as local, but it was class-level); (4) `count(*)`-with-filter and filter-plus-order-by-unindexed queries returning **500s** (statement timeouts, not logic bugs); (5) an analytical headline declared "REAL" without checking that it survived a **main-effect vs best-cell** comparison and an out-of-sample test spanning more than one time window. Each was caught only because the numbers were re-checked against ground truth, not the logs. Joe: *"lots of the constant mistakes and fixes here are likely common across different builds — ensure it lives in Bob so we don't keep making them."*
- **Decision:** Add **Rule 26 — Keep the machine hermetic & refactor by invariant** (the engineering twin of Rule 25): imports must be **side-effect-free** (read creds/config lazily); refactor against a **reproducibility invariant** (capture a deterministic output, assert bit-identical after EACH step); moving a shared module is a **class-level** change (grep every importer incl `package.json`/CI/other pipelines; shim live consumers, never leave import-broken); know the **DB statement-timeout traps** (`count=estimated`; keyset on indexed cols); report **honest parallel speedups** (pandas/groupby is memory-bandwidth-bound); and the **patchwork→one-machine consolidation shape** (one builder · one config/factor catalog the engine reads · guards as a pipeline invariant · results ledger for endpoint tracking · config-driven CLI · archive the scratch — invariant-checked each step). Also **extended Rule 25** with two data catches from the same sessions: census **LOADED-N vs source count(\*)** per partition (silent pagination/LIMIT truncation), and **main-effect-vs-best-surviving-cell** (de-dupe survivors by stat-signature, require ≥K non-overlapping OOS windows, control for known dominant factors, backward-only derivations). Rules 25→26; lens library unchanged (37). Wired across `build-protocol-core.md` + `skill/SKILL.md`; recorded here.
- **Consequences:** Bob now front-loads the engineering-hygiene checks a non-engineer would never think to demand, so a green build/CI is no longer mistaken for a correct one at the *plumbing* layer either. Cost: Rule 26 adds six checkpoints that mostly matter on refactors/consolidations/data-pulls (cheap to skip-when-N/A, loud when they bite). The consolidation shape is now a named EVOLVE-mode target, not a bespoke re-invention each time a codebase accretes scripts.

### D-011: Supervised Autonomy — reduce build-phase babysitting via milestone gates, NOT a swarm (Rule 27)

- **Date:** 2026-08-06
- **Status:** Accepted (v2.34); HARDENED v2.35 (2026-08-07) via an adversarial self-audit + free-resource scrape before first real use — fixed the green-gate infinite-loop footgun (loop-guarded script), reframed deny-rules-vs-classifier, documented the `auto`-ignored-in-project-settings trap + a runbook, wired the reviewer's invocation, and added the headless-abort ceiling + `/sandbox` + real spend cap. See v2.35 changelog.
- **Context:** Joe: every Bob build is ~5–7 days of pressing "continue" every ~20 min — mostly mechanical babysitting on the build/verify loop. He asked whether agent swarms (Hermes-style) can now run a detailed plan end-to-end. Research (Aug 2026, cross-verified: METR time-horizons, Berkeley MAST, Anthropic telemetry, field trials) is unambiguous: fully-hands-off multi-subsystem builds are unproven (agents reliably work ~30–70-min chunks; "done" is the least-trustworthy signal; ~76% of failures are false-success), and multi-agent **swarms make CODING worse** (coordination failure 41–87%, ~15× cost — the field retreated from free-form swarms toward orchestrator + gated subagents). ### D-014: A recurring defect class is escalated, not re-documented; and Bob harvests incidents from the field

- **Date:** 2026-09-18
- **Status:** Accepted
- **Context:** The founder asked why a two-week defect wave happened inside a product built and audited under this protocol — *"it's so bizarre that we just spent hundreds of hours trying to fix stuff that we theoretically had already scoped out and never had detected."* A six-agent census of 2026-09-06→18 measured it: **68 defects** in the decision log, **86 more** caught in review on six PRs alone, **179 merged PRs** of which **40% were fixes** and **26% were fixes for fixes** (chains three deep). Detection was almost entirely human: fresh-context audits found 44%, the builder's own later pass 25%, the founder 19% — **all automation together, 12%**, and **only 3 of 86** review findings were catchable by a unit or integration test. The obvious remedy — write the lessons into the audit checklist — had **already been run and failed**: the dominant class (a read ERROR treated as "no data," so a failure becomes an empty value a builder then persists) had a standing written rule in an always-loaded memory index and **recurred ~40 times** through six successive fixes. A parallel census of ~130 *process* failures found **~95 occurred while a correct, written, project-local rule already existed**; only ~15 were genuine knowledge gaps. Two controlled experiments confirmed the diagnosis: fresh readers with **no checklist and no project context** caught 3 of 4 real defects cold (each volunteering additional real defects the prompt had not planted), and a checklist arm on the same defect detected nothing the unaided arm missed. The one miss was a defect of *omission* — a monitoring capability nobody built — which no amount of reading can surface.
- **Decision:** Three rules plus two mechanisms. **Rule 31 (intervention ladder):** when a class recurs after a fix, escalate a tier rather than re-stating the rule — write-it-down → *calibrated* mechanical check → fresh-context read → make the defect unrepresentable. Only tier 4 ended the recurring class in the field (a `T | null` return became a four-state discriminated union so the compiler forces every caller to name its case, and the duplicated loop was deleted rather than doubly guarded). **Rule 32 (incident intake):** every production incident exits through failure-mode → the one mechanically-checkable question → owning lens/rule, **or `NONE`**; a `NONE` is a framework gap recorded in a new **failure-mode index** and given a fixture. **Rule 33 (dogfooding):** `coherence-check.sh` runs on Bob itself, `audit-ledger.json` ships as a template `bob-init` creates, and every rule carries an enforceability tag. Rule 24's trigger map gains a fifth, **structural-code-event** class (a shared reader gaining a caller of a different class; a second copy of a loop/guard/config derivation; a guard added to one of several sibling lanes; a migration altering another's object; a job gaining a trigger/budget/timeout/concurrency group; a dependency major; a stub or receipt being written) — because every trigger Bob had was a document or phase event, and every defect in the census was born mid-phase inside an ordinary small change.
- **Alternatives considered:**
  - *Add lens content for each new failure family.* **Rejected on evidence.** The controlled test shows content is not the binding constraint for defects of commission, and the field shows a written rule failing ~40 times. Adding prose to a library where 2 of 30 rules have an enforcer makes the ratio worse.
  - *Ship a grep-based check for the dominant class.* **Built, measured, rejected.** Naive pattern flags 11 files of ordinary safe-navigation; scoped to builder modules it still yields 45 mostly-legitimate hits, because the defect is a *dataflow* property and grep sees only *syntax*. Shipping it would violate Rule 28's own calibration discipline. Recorded as a negative result in the fixture so it is not re-derived.
  - *Make every change Tier 1 (always a fresh audit).* Rejected — 179 PRs in 12 days; a full fresh audit per change is unaffordable. The structural-event trigger is the targeted form: a scoped read of one seam, minutes not hours.
  - *Rewrite Rule 27's "sequential, not parallel" stance.* Deferred to its own evolution. The project ran three parallel sessions for two weeks using conventions Bob lacks (lane ownership, a DB write-lane lock, worktree-per-session, single-owner SSOT files, PR-only through one integrator) — evidence Bob's avoidance posture is now too strong, but changing it needs its own evidence base.
- **Consequences:**
  - The failure-mode index publishes an uncomfortable scoreboard: **41 rows, 14 owned, 27 NONE, 7 with fixtures.** That is deliberate. It is not a mandate to write 27 lenses — several of those rows (calendar-vs-event cadences, parallel-agent clobbering, stale index lines) are things **Bob does wrong itself**.
  - Bob is now on record as failing three of its own checks (three duplicate decision IDs, drifting lens counts, a missing `audit-ledger.json` that three rules gate on). Fixing them is follow-on work; **this entry does not fix them, and the duplicate IDs are left intact deliberately** — renumbering would break inbound references, and the right repair is a decision from the owner, not a silent rewrite by a tool.
  - Rule 31 makes some fixes more expensive on purpose: a recurring class may no longer be closed by a note. The trade is against ~26% of PRs currently being fixes for fixes.
  - The fixture corpus gives Rule 28's long-standing "regression-test every check" requirement a harness for the first time, and gives any future rule a falsifiability test.
- **Revisit trigger:** (a) a class recurs *after* being closed at tier 4 — the ladder is wrong or tier 4 was mis-applied; (b) structural-event triggers fire so often they are ignored — narrow the event list using the ledger; (c) the failure-mode index's NONE count does not fall over two quarters — intake is being skipped, and Rule 32 needs an enforcer rather than prose (which would be Rule 33 applied to Rule 32); (d) a fixture's baseline and treatment arms diverge, proving a checklist *does* add detection value for some class — then the Rule 31 ladder's tier ordering needs revisiting for that class.

### D-019: /bob UPGRADE — existing projects get Bob's improvements on purpose; rules live in one of three layers; Bob carries its own Engineering Principles

- **Date:** 2026-10-27
- **Status:** Accepted
- **Context:** Bob's improvements reached only projects started after them. `bob-init` "skips anything that already exists", so D-017's guard hooks and D-018's merge guard, audit ledger and daily check never arrived in any project begun earlier, and D-018 said so in its own Consequences. Nothing recorded what Bob had installed or from which version, so nobody could tell Bob's later changes from a project's deliberate ones. Separately, the same rules had piled up in three places — the author's private global instructions, Bob, and project files — and copies drifted. Two of Bob's lenses (L31, L37) cited "Engineering Principle #2 / #7" from that private global file, which public readers cannot see, and one failure-mode row (B7, a refactor that keeps the names but drops the runnable entry point) admitted its rule lived "in the founder's CLAUDE.md, not in Bob". Finally, a machine-wide commit hook that chains the coherence sweep (the documented setup when git's hooks folder is set globally) can look for Bob in a folder that no longer exists — and then the sweep silently never runs; one such hook had never run it at all.
- **Decision:**
  - **UPGRADE mode (`SCRIPT`).** A fourth mode in the menu. `scripts/bob-upgrade.mjs`, run from the project folder, lists every piece Bob installs (the hook files and their `.claude/settings.json` entries, the reviewer, the green gate, the daily dropped-work check, the lists Bob creates once, the Bob pointer in CLAUDE.md, two optional templates, and whether the commit-time sweep blocks) as up to date / Bob has a newer version / missing / changed here on purpose / changed here with no reason written down — with the decision-log entries behind each change, found from Bob's git history. Report-only by default; `--apply all|<items>`, `--interactive`, `--enforce <items>`. **Bob's current version of each piece is what `bob-init` writes today** — the script runs `bob-init` in a throw-away folder rather than keeping a second copy of the content. `bob-init` now records what it installed and from which Bob commit in `.bob/installed.json` and writes an empty `.bob/differences.md` (template `templates/bob-differences.md`): one line per deliberate difference, with its reason; UPGRADE never touches those. A project with no record is compared with every past version of each file in Bob's history. Safety: nothing outside the installed set (plus `.bob/`) is touched; every replaced file is copied to `.bob/backups/<date>/` first; the project's own test command in `green-gate.sh` is kept.
  - **Warn-only first (`HOOK`).** `scripts/hooks/warn-only.mjs` runs a hook and turns a block into a visible warning. UPGRADE adds any hook that can stop work through it; `--enforce` switches it to blocking. The merge guard is the exception — it has no off switch (D-018) — and its soft start remains the empty required-checks list.
  - **The commit-time sweep blocks only on request.** The sweep (in `bob-init`'s per-repo hook and the documented global-hook chain) blocks only where `.bob/installed.json` says `"commit_sweep": "block"`; elsewhere it prints the problems and lets the commit through. `bob-init` writes "block" for a new project; an existing project stays warn-only until UPGRADE switches it, which it refuses while the documents fail.
  - **Three layers (`PROSE`).** `build-protocol-core.md` §"WHERE RULES LIVE" and the README's "How Bob fits with your own setup": global instructions (any task) · Bob (the one method for building software) · project (its facts + deliberate differences). Write a rule once in the lowest layer that covers it; point, don't copy. Backwash (a project's better idea goes back into Bob in general terms) and UPGRADE are the two directions of one loop.
  - **Engineering Principles 1–9 in Bob (`PROSE`).** `build-protocol-core.md` §"ENGINEERING PRINCIPLES", numbered so existing citations stay right. New in Bob: **5** — changed function inputs → update every caller in the same change; **8b** — a refactor must keep the runnable entry point, not just the importable names (both also as Rule 26 bullets; failure-mode row B7 now owned); **8a** — the obvious cause is often a red herring, check what the last good run used (Debugging Protocol step 1); **9** — a "the tool can't do that" note must name the version it was checked against and expires; a "we chose not to" note doesn't. Debugging Protocol gains step 5b, read two neighbouring code paths. L31 and L37 now cite Bob's own section.
- **Alternatives considered:**
  - *Re-run `bob-init` on old projects.* Rejected — it skips existing files by design, so it can add what is missing but never update what is stale, and it cannot tell a deliberate change from an old copy.
  - *Keep a copy of every piece's content inside the upgrade script.* Rejected — a second source that would drift from `bob-init`; running `bob-init` in a throw-away folder keeps one.
  - *Add each new hook already blocking.* Rejected — a project running without a hook has habits the hook may refuse; blocking on day one stops work the owner did not choose to stop. Warn-only first makes switching on a decision.
  - *Switch on the commit-time sweep everywhere at once.* Rejected — run against the author's existing Bob projects, one would have been blocked on its next commit by stale file pointers in its root instruction file. Blocking is per project, after its documents pass.
  - *Leave the principles in the private global file and keep citing them.* Rejected — Bob is public and must read on its own.
- **Consequences:**
  - Existing projects can take Bob's improvements without losing their own changes, and every change arrives with its reason. Cost: the report runs `bob-init` once (well under a second) and, where `docs/build-manifest.md` exists, the coherence sweep (seconds on a large document set).
  - Comparing `.claude/settings.json` hook entries means rewriting that file as two-space JSON when an entry is applied; the old copy is backed up first.
  - Pieces without their own source file (the reviewer, the green gate, the settings entries) can only be matched against Bob's current version when a project has no install record; they show as "can't tell who changed it" rather than "older Bob".
  - The commit-time sweep now actually runs in Bob projects on the author's machine, warn-only until each is upgraded. On a large document set it adds several seconds to every commit there.
  - `scripts/selftest-gate-scripts.sh` grows by 39 cases on fixture projects scaffolded from an older Bob (fresh; pieces missing; deliberate and unexplained differences; no install record; the commit-time sweep refused then switched on; warn-only then enforced).
- **Revisit trigger:** (a) a project reports a piece as "changed here" that it never touched — the comparison is wrong; fix it with that project's case as a fixture; (b) Claude Code changes how a hook's JSON reply or exit code 2 is read (checked 2026-10-27, as in D-018) — re-check `warn-only.mjs`; (c) a Bob piece gains a line projects are expected to customise (like the green gate's test command) — give it a `normalize` rule in the piece list, or UPGRADE will call every project's copy "changed".

### D-020: UPGRADE fixes from a fresh-eyes audit — a project's own tools count, the green gate waits for a real test command, the merge guard says how to recover, short paths resolve, and the commit check judges what is being committed

- **Date:** 2026-10-27
- **Status:** Accepted
- **Context:** A fresh-context audit of D-018/D-019, plus running `/bob UPGRADE` report-only on two real projects, found: (1) **material** — the upgrade called a piece "missing" and put it in `--apply all` when the project already did the same job with its own tool (its own merge guard wired from `scripts/`, its own loop check), so "apply every safe update" would have installed a second, competing guard; (2) **material** — `--apply all` would switch on the green gate while its test command was still `bob-init`'s placeholder, which fails by design, so Claude would be stopped at the end of every task; (3) a missing or damaged `.claude/required-checks.json` refused every merge with no way out stated, and `config-protection.js` told Claude to "fix the source code" for that file; (4) the root-file pointer check failed on short paths that exist (`send-email/index.ts` under `supabase/functions/`) and on section numbers that are not headings; (5) the commit-time check read files on disk, so in blocking mode one session's half-finished, unstaged edits could stop another session's commit, and when Bob was not found it skipped silently even in a project that asked to be blocked; (6) the Bob pointer went into a `CLAUDE.md` that only says `@AGENTS.md`; (7) `bob-update-check.sh` read the version from `CLAUDE.md` (now a one-line pointer) and always showed "?", and `AGENTS.md` restated the version and had fallen nine releases behind; (8) report wording used terms a non-engineer reader has to look up.
- **Decision:**
  - **"Project has its own version"** (`SCRIPT`). Before calling a piece missing, `bob-upgrade.mjs` looks for a same-job tool by name (merge-guard, loop-check, green-gate, block-no-verify, config-protection) in the project's hook commands (`.claude/settings.json` / `settings.local.json`; for a settings piece, only on the same event) and in the usual script folders. Bob's own install paths never count, and when Bob's own entry is still wired, Bob's file is genuinely missing. Found → reported with its path, left alone, never in `--apply all`; naming it still installs Bob's. Bob's settings entries are now recognised only by `.claude/hooks/<file>`, so a project's `scripts/merge-guard.mjs` is no longer mistaken for Bob's entry.
  - **Green gate waits for a real test command** (`SCRIPT`). While `TEST_CMD` is the placeholder, the switch is "waiting for your test command" (with how to set it), is left out of `--apply all`, and `--apply`/`--enforce` of it refuse.
  - **Recovery, in plain words** (`HOOK` text). The merge guard's no-list refusal and `config-protection.js`'s message for `required-checks.json` both give the owner's Terminal command that resets the list to the "no CI yet" stage (`cp ~/.claude/skills/bob/../templates/required-checks.json .claude/required-checks.json`) and say the owner can always merge by hand. UPGRADE reports a list it cannot read as "damaged" and restores it only when named, backing up the old copy (never in `--apply all`: resetting loosens the guard, so it is the owner's call).
  - **Pointer check** (`SCRIPT`). A path with a "/" that does not resolve counts as found when exactly one repo file ends with it (node_modules and .git skipped); two or more is a warning; none fails. A "§N of file" fails only when the file is missing; a missing section is a warning.
  - **One commit-check script** (`SCRIPT`). New `scripts/commit-sweep.sh` holds the logic both `bob-init`'s per-repo hook and the global-hook chain call. In blocking mode, a failure on disk is re-checked on a copy of the staged files (`git checkout-index`), and the commit is stopped only if that fails too. No extra cost when the check passes. Bob not found in a project set to block → a loud warning with the fix, commit not blocked (a missing install must not stop all work).
  - **Smaller.** The pointer goes into `AGENTS.md` when `CLAUDE.md` only imports it. The version is read from `build-protocol-core.md`'s first line everywhere; `AGENTS.md` now points there. Report text is plain ("safety check [hook]", "trial mode", "stops"), duplicate headings merge, and `--apply all` no longer prints a line per up-to-date item.
- **Alternatives considered:** *Detect "own version" by comparing behaviour, not names* — rejected: no reliable way to run another project's tool safely; names plus the hook slot are cheap, and a false "own" only means "left alone", the safe direction. *Run the commit check only on staged files always* — rejected: copying the staged tree on every commit costs time on large repos; doing it only after a failure keeps the passing path free. *Block when Bob is missing in a blocking project* — rejected: one broken install link would stop every commit in every Bob project on that machine.
- **Consequences:** `--apply all` can no longer install a duplicate guard or a gate that always fails. A problem present only in the staged copy while the disk is clean passes once (rare; the next commit catches it). A machine with an older Bob (no `commit-sweep.sh`) gets a warning from the global hook instead of a check until it pulls. `selftest-gate-scripts.sh` grows from 165 to 205 cases; the merge guard's suite from 318 to 319.
- **Revisit trigger:** (a) a project's tool is reported as "its own version" when it does a different job — tighten that name pattern with the case as a fixture; (b) the staged re-check takes over ~2 s on a real repo — copy only the files the check reads.

    - the integration playbooks' numbers L1–L11 clashed with the audit lenses L01–L38;
    - the four history folders sat at the top level.
- **Decision:**
  - (1) **Five new checks**, each tied to a rule, tested in the self-test, and reached from the phase gate (items 13–15), the Supervised Autonomy runbook (its new step 0) or Bob's CI:
    - `scripts/phase-report-check.mjs` (Rule 4; Phase Gate 13). It refuses a phase report whose always-required sections are missing, empty, or still the template's placeholder text. It reads the section list from `templates/phase-report.md`, so that list keeps one home.
    - `scripts/run-commands-check.mjs` (Rule 26 and Engineering Principle 8b; Phase Gate 14). It compares a change with git and refuses when a run config (package script, CI step, Makefile, Procfile, schedule …) still names a file the change deleted or renamed, or a Python file that lost its run block.
    - `scripts/autonomy-check.mjs` (Rule 27; runbook step 0). It runs before a hands-off phase and checks the deny and ask rules, a green gate with a retry limit and a real test command, a reviewer that cannot edit, no ignored `defaultMode: "auto"`, and no production key in the settings.
    - `scripts/recurrence-check.mjs` (Rule 31; Phase Gate 15). It reads `Class:` and `Rung:` lines in fix commits and refuses a class fixed twice whose newest fix is below rung 3.
    - `scripts/rule-tags-check.mjs` (Rule 33, in Bob's CI). Every rule the index tags as checked must name a script that exists and that CI or the self-test runs.
    - Each check exits 2 (cannot judge) rather than 0 when it has nothing to read (Rule 29).
    - A third review found the remaining edge cases: italic text in a report, a retry limit written as a plain number, class names that differ only in case or a trailing full stop, and a later commit that names a class without a rung. Each was fixed and became a self-test. Rule 4 is tagged `SCRIPT` (in part), because the check can see that "Spec Deviations" was filled in, not that what it says is true.
    - A fresh review found nine serious problems in the first version, most of them false alarms on healthy projects. All were fixed and turned into self-tests before release:
      - the phase-report check now accepts other heading styles, any "N/A" or "None" line, and the short report the Minimum Viable Process allows (`--abbreviated`);
      - the run-commands check follows `cd`, workflow and job defaults, matrix folders, build output and installed tools, and it passes an app whose scripts only call tools;
      - the autonomy check ignores personal Stop hooks, accepts an overridable retry limit, refuses a reviewer with no tools line, and reports a project that was never set up as "cannot judge" rather than as six failures;
      - the recurrence check reads only real git trailers;
      - the rule-tags check needs a real call, not a mention in a comment, and compares the whole tag. It found that Rule 32 was tagged one way in `rules.md` and another in the index, and that was fixed.
    - A second fresh review found eight more. They were fixed the same way, and again each became a self-test:
      - the run-commands check was narrowed to commands it could read for sure (a third review still found shapes it got wrong, so it was rebuilt; see Consequences);
      - the phase-report check keeps sub-headings inside their section, accepts "N/A" in a heading, and reads the short-report list from the template;
      - the autonomy check understands the hook quoting Claude Code's docs use, retry limits written in any language, and stricter deny rules;
      - the recurrence check reads `Class:` / `Rung:` lines anywhere outside code blocks, so a Co-Authored-By line after them is fine;
      - the rule-tags check matches a script's own path.

      The review also showed that two tags claimed more than was wired, so the recurrence check became Phase Gate 15 and the autonomy check became step 0 of the Supervised Autonomy runbook.
    - The Supervised Autonomy setup text no longer tells users to set `defaultMode` to "auto" in the project file, which the runbook and the new check both say does nothing.

    The index now lists 24 rules as written-only, down from 28. Rule 22 (the pre-build gate) was not given a check here, because its text and the build manifest it would read are in the NEW mode, which the ORCHESTRATE session is rewriting.
  - (2) Rule 27 in `rules.md` keeps the rule, its hard boundaries, the new setup check and a pointer. The how-to lives only in `build-protocol.md` § Supervised Autonomy. The one detail that section lacked (diff the test files; prefer a reviewer from a different model family) was added to its runbook step 4, with its owner's agreement.
  - (3) Rule 31's ladder steps are called rungs. The Minimum Viable Process groups are "Never skip / Skip with caution / Skip first". In the core and `rules.md`, "Tier" now means only Rule 30's tiers (a few lenses keep tiers of their own, such as L34's).
  - (4) `bob-doctor.sh` checks that both design skills are linked from the same Bob copy and prints the line to paste if not. The README install prompt asks for all three skills.
  - (5) Method text says "the user" where it meant whoever is using Bob, and "Bob's author" where it records where an idea came from. Credit, licence and dated source lines keep the name. ORCHESTRATE's own files are left to their owner.
  - (6) The playbooks are numbered P1–P11. The retros carry a snapshot note. Three living files carry `<!-- living doc -->`. The orphan retro is linked from Rule 32.
- **Alternatives considered:**
  - Group `evolutions/`, `retros/`, `lens-retros/` and `fixtures/` under one `history/` folder. Not done, by choice: `fixtures/` is test data that ORCHESTRATE's tests and the failure-mode check read; the others are linked from dated changelog and decision-log entries that must not be rewritten; and `AGENTS.md`'s file map already groups them as history. A cosmetic gain did not justify breaking those links.
  - A recurrence check that guesses the class from the commit wording. Rejected: it would raise false alarms, and Rule 31 says a check that cries wolf gets muted. It reads explicit lines instead, and says so when there are none.
  - Build a check for Rule 22 now. Deferred to the NEW-mode rewrite, for the reason above.
- **Consequences:**
  - The phase gate has 15 items.
  - A project's fix commits need two short git trailer lines for the recurrence check to see them; the phase report's class-level scan section now says so. Without those lines it reports "cannot judge", never "clean".
  - The autonomy check reads only the project's own settings, because personal rules do not travel with the project. A user whose deny rules live only in their personal settings is told to add them to the project.
  - The run-commands check was rebuilt after the third review. Its first design read every run command and judged whether the file it named existed. Each of three fresh reviews found new healthy command shapes it judged wrong: wrappers, subshells, monorepo filters, files made while the job runs, `.ONESHELL` Makefiles. That is three rounds of the same fix failing, so the approach was changed rather than patched a fourth time. It now judges the change: it asks git what the change deleted, renamed or stripped of its run block, and refuses only when a run config still names that file. Run over long stretches of real history in several projects, it raised no false alarm. The cost is deliberate: it cannot see a command that was already broken before the change.
  - The autonomy check, run on a fresh `bob-init` project, refuses only the test command the user has not filled in yet. That is deliberate: until it is filled in, the gate blocks every stop.
- **Revisit trigger:**
  - The NEW-mode rewrite lands: build the Rule 22 check.
  - Or: any of the new checks raises a false alarm on a healthy project. Fix the check or remove it; never mute it.

## Anti-pattern reminder

ADRs that describe the decision without consequences are useless. The Consequences section is where future-you discovers why the seemingly clever shortcut is the thing now blocking a new requirement. Every decision in this file has a Consequences block — keep it that way.
